## ADDED Requirements

### Requirement: Sequential phase execution
The pipeline SHALL execute phases in strict forward-sequential order: Phase 1 (DS Bootstrap) → Phase 2 (Token Engine) → Phase 3 (Component Generation) → Phase 4 (Documentation & Governance) → Phase 5 (AI Semantic Layer + Analytics) → Phase 6 (Release). Phase N+1 SHALL NOT begin until Phase N is complete or has been marked failed. Within Phase 3, Design-to-Code Crew SHALL run before Component Factory Crew. Within Phase 4, Documentation Crew SHALL run before Governance Crew.

#### Scenario: Normal phase progression
- **WHEN** Phase 1 completes successfully
- **THEN** the pipeline SHALL immediately begin Phase 2
- **AND** SHALL NOT skip, reorder, or parallelize Phase 3 ahead of Phase 2

#### Scenario: Phase 5 internal ordering
- **WHEN** Phase 5 begins
- **THEN** AI Semantic Layer Crew and Analytics Crew MAY run in either order (no mutual dependency)
- **AND** both SHALL complete before Phase 6 begins

### Requirement: Component-level retry protocol
For Phase 1–3 generator/validator pairs, the pipeline SHALL implement a per-component bounded retry loop with a maximum of 3 retry attempts. The validator SHALL produce a structured rejection specifying: which checks failed, the exact errors, and a suggested fix. Each retry attempt SHALL include all prior rejection feedback appended to the original task context. A component that fails after 3 attempts SHALL be marked `failed` in the generation report and the pipeline SHALL continue with remaining components.

#### Scenario: Component fails validation on first attempt
- **WHEN** a generated component fails spec validation
- **THEN** the validator SHALL produce a structured rejection with check names, error details, and suggested fix
- **AND** the rejection SHALL be fed back to the Code Generation Agent as context appended to the original task
- **AND** the Code Generation Agent SHALL produce a corrected output

#### Scenario: Component exhausts retry limit
- **WHEN** a component has failed validation 3 times
- **THEN** the Rollback Agent SHALL preserve the component's last best attempt
- **AND** the component SHALL be marked `failed` with full error traces in `reports/generation-summary.json`
- **AND** the pipeline SHALL continue generating remaining components

#### Scenario: Accumulating rejection context
- **WHEN** retry attempt 3 begins for a component
- **THEN** the Code Generation Agent SHALL receive: the original task, the rejection from attempt 1, AND the rejection from attempt 2 — all in context
- **AND** SHALL NOT receive only the most recent rejection

### Requirement: Retry boundaries for Phases 1–3
The retry protocol SHALL apply at the following generator/validator boundaries:
- Token Foundation Agent (2) ↔ Token Validation Agent (8): naming violation, contrast failure, broken reference
- Code Generation Agent (14) ↔ Spec Validation Agent (17): missing props, invalid state transitions, broken token refs
- Code Generation Agent (14) ↔ Render Validation Agent (15): render failure, empty output, visual artifact
- Code Generation Agent (14) ↔ TypeScript Compiler: type errors, import errors
- Accessibility Agent (19) ↔ axe-core: critical a11y violation after patching
- Accessibility Agent (19) ↔ TypeScript Compiler + Render Validation Agent (15): a11y patches introduced type errors or render regressions

#### Scenario: Token naming violation triggers retry
- **WHEN** the Token Validation Agent detects a naming convention violation in an output token
- **THEN** the structured rejection SHALL include the token name, the violated rule, and the suggested corrected name
- **AND** the Token Foundation Agent SHALL be re-invoked with the rejection as additional context

#### Scenario: Post-a11y-patch re-validation failure
- **WHEN** the Accessibility Agent applies patches to a component's `src/` file
- **AND** re-compilation with `tsc --noEmit` produces a type error
- **THEN** the type error SHALL be fed back to the Accessibility Agent as a retry trigger
- **AND** the retry loop SHALL re-apply patches and re-validate

### Requirement: Cross-phase retry routing via First Publish Agent
The First Publish Agent (Agent 6) SHALL handle cross-phase retry routing. When a Phase 2 validation crew rejects Phase 1 output, the First Publish Agent SHALL detect the failure, re-invoke the originating Phase 1 agent with the rejection context, then re-run the Phase 2 crew. Cross-phase retry SHALL respect the same 3-attempt limit as within-phase retries. Before each re-run the Rollback Agent SHALL restore the checkpoint from before the re-invoked phase to prevent artifact corruption.

#### Scenario: Phase 2 validation rejects Phase 1 token output
- **WHEN** the Token Validation Agent (Phase 2) rejects tokens generated by the Token Foundation Agent (Phase 1)
- **THEN** the First Publish Agent SHALL re-invoke the Token Foundation Agent with the structured rejection
- **AND** SHALL restore the pre-Phase-1 checkpoint via the Rollback Agent before re-running
- **AND** SHALL re-run the Token Engine Crew after the corrected Phase 1 output is written

### Requirement: Phase 4–6 crew-level retry
For Phases 4–6 (Documentation, Governance, AI Semantic Layer, Analytics, Release), the retry protocol SHALL operate at the crew level, not per-agent. If a Phase 4–6 crew fails, the First Publish Agent SHALL retry the entire crew up to 2 attempts. If a crew exhausts 2 attempts, it SHALL be marked `failed` in the generation report and the pipeline SHALL continue. Phase 4–6 failures SHALL be non-fatal to the core design system (components, tokens, tests already validated).

#### Scenario: Documentation Crew fails on first attempt
- **WHEN** the Documentation Crew produces invalid Markdown or an incomplete output
- **THEN** the First Publish Agent SHALL retry the entire Documentation Crew once more
- **AND** if the second attempt also fails, SHALL mark Documentation Crew as `failed` and advance to Governance Crew

#### Scenario: Release Crew failure is non-blocking
- **WHEN** the Release Crew fails on both attempts
- **THEN** the pipeline SHALL write the failure to `reports/generation-summary.json`
- **AND** the components, tokens, and tests already on disk SHALL remain intact and usable

### Requirement: Checkpoint persistence at phase boundaries
The Rollback Agent SHALL write a timestamped checkpoint snapshot of the entire output folder at each phase boundary. Each checkpoint SHALL include all files present in the output folder and a manifest listing expected files and their checksums. The checkpoint format SHALL be a versioned directory alongside the output folder (not inside it) to avoid being swept by rollback.

#### Scenario: Checkpoint written at phase boundary
- **WHEN** Phase 2 completes successfully
- **THEN** the Rollback Agent SHALL write a checkpoint snapshot capturing all files in the output folder at that moment
- **AND** the checkpoint manifest SHALL list all written files with their checksums

#### Scenario: Checkpoint integrity validation on resume
- **WHEN** the CLI starts with `--resume`
- **THEN** the Rollback Agent SHALL read the checkpoint manifest and verify that every listed file is present and has a matching checksum
- **AND** SHALL report any missing or corrupted files before resume begins

### Requirement: Rollback cascade policy
When the Rollback Agent restores a checkpoint from phase N, all artifacts produced by phases N+1 and later SHALL be invalidated. The pipeline SHALL re-run all phases from N+1 onward after rollback. The First Publish Agent SHALL NEVER resume mid-sequence after a rollback — it SHALL always re-run from the phase immediately following the restored checkpoint.

#### Scenario: Rollback to pre-Phase-3 checkpoint
- **WHEN** the Rollback Agent restores the checkpoint from the end of Phase 2
- **THEN** all `src/` files written by Phase 3 (including any in-place a11y patches) SHALL be removed
- **AND** Phase 3 SHALL re-run in full from the restored checkpoint

### Requirement: Plugin architecture for tools
Every tool, compiler, and linter used by agents SHALL be registered as a plugin via `pipeline-config.json`. Crews SHALL invoke tools through a registered plugin interface — they SHALL NOT call compilers or linters directly. The plugin system SHALL allow swapping implementations (e.g., replacing the token compiler) without modifying pipeline core code.

#### Scenario: Plugin invocation
- **WHEN** the Token Compilation Agent invokes the token compiler
- **THEN** it SHALL call the registered plugin by its `pipeline-config.json` identifier
- **AND** the plugin interface SHALL abstract the concrete tool implementation from the agent

#### Scenario: Plugin not registered
- **WHEN** an agent attempts to invoke a tool that is not registered in `pipeline-config.json`
- **THEN** the pipeline SHALL fail-fast with an error identifying the missing plugin before the phase begins

### Requirement: Exit criteria
Before the pipeline marks the final generation as complete, the Pipeline Completeness Agent (Agent 34) and the Quality Gate Agent SHALL collectively verify the 15 exit criteria defined below. Each criterion has a severity: **Fatal** (pipeline MUST NOT be marked `isComplete: true` if this fails) or **Warning** (pipeline IS marked complete but the criterion is surfaced in the output review).

**Fatal criteria (8) — pipeline incomplete if any fail:**
1. Token JSON parses without error (`JSON.parse` validation)
2. Token JSON conforms to W3C DTCG schema (JSON Schema validation of `$value`, `$type` keys)
3. All semantic token references resolve to global tokens (reference graph traversal)
4. All component token references resolve to semantic tokens (reference graph traversal)
5. All foreground/background color pairs meet WCAG target (contrast ratio calculation per theme)
6. CSS custom properties have no undefined references (regex + token map scan of compiled CSS)
7. TypeScript compiles with zero errors (`tsc --noEmit` across all `src/`, `tests/`, and story files)
8. `npm install` and `npm run build` complete without errors; `dist/` is non-empty

**Warning criteria (7) — pipeline marked complete, but surfaced in output review:**
9. All unit tests pass (Vitest — test failures are non-blocking; `hasTestFailures: true` is set but `isComplete` remains `true`)
10. No hardcoded color/spacing values in source (AST scan — violations listed in `reports/token-compliance.json`)
11. All interactive components have ARIA roles (AST scan — violations listed in `reports/a11y-audit.json`)
12. All components score ≥70/100 on quality gate (Quality Scoring Agent — below-threshold components flagged)
13. Spec ↔ code ↔ docs consistency check passes (Drift Detection Agent — drift entries in `reports/drift-report.json`)
14. Component registry JSON is valid and complete (schema validation of `registry/components.json`)
15. One or more components are marked `failed` in the generation summary (flagged in output review)

**Note:** Test failures (criterion 9) are classified as Warning, not Fatal. In an AI-generation pipeline, some generated tests may fail despite correct component output. Test failures are surfaced prominently in the output review but do not block `isComplete: true`. Build failures (`npm install` and `npm run build`) remain Fatal.

#### Scenario: Exit criteria 1 fails — fatal (token parse error)
- **WHEN** any token JSON file fails `JSON.parse`
- **THEN** the pipeline SHALL NOT set `"isComplete": true` in the generation summary
- **AND** the CLI SHALL report the parse error details before presenting the output review

#### Scenario: Exit criteria 5 fails — fatal (WCAG contrast)
- **WHEN** a semantic foreground/background color pair fails the configured WCAG contrast target in any theme
- **THEN** the pipeline SHALL NOT set `"isComplete": true` in the generation summary
- **AND** the CLI SHALL list the failing token pair, measured ratio, and required ratio

#### Scenario: Exit criteria 8 fails — fatal (build failure)
- **WHEN** `npm install` or `npm run build` exits with a non-zero error code
- **THEN** the pipeline SHALL NOT set `"isComplete": true` in the generation summary
- **AND** `reports/generation-summary.json` SHALL set `"hasBuildFailure": true`

#### Scenario: Exit criterion 9 is warning only (test failures)
- **WHEN** `npm test` reports failing tests after a successful build
- **THEN** the pipeline SHALL still set `"isComplete": true` for the overall run
- **AND** `reports/generation-summary.json` SHALL set `"hasTestFailures": true` with the failing test names

#### Scenario: Exit criterion 15 is warning only (failed components)
- **WHEN** exactly one component exhausted its retry limit and is marked `failed`
- **THEN** the pipeline SHALL still set `"isComplete": true` for the overall run
- **AND** the generation summary SHALL include the warning in the output review section

#### Scenario: All 15 criteria pass
- **WHEN** all 8 fatal and all 7 warning criteria are satisfied
- **THEN** `reports/generation-summary.json` SHALL set `"exitCriteria": { "allFatalPassed": true, "warningCount": 0, "isComplete": true }`

### Requirement: Human Gate — Output Review
After the Release Crew completes (Phase 6), the pipeline SHALL pause and present the Output Review gate to the user before finalizing the run. The CLI SHALL display a summary of: components generated vs. failed, quality gate results, exit criteria status, any warnings, and the output folder path.

The user SHALL have four available actions at the Output Review gate:

1. **Accept** — mark the generation run as accepted; the CLI exits with success
2. **Reject** — mark the run as rejected; the CLI exits with a non-zero status and notes the rejection reason in the generation summary
3. **Re-run from phase** (`--from-phase N`) — re-run the pipeline from Phase N onward using the existing output folder
4. **Retry components** (`--retry-components Name1,Name2,...`) — re-run the Design-to-Code and Component Factory crews only for the specified component names

Actions 3 and 4 cause the pipeline to re-enter the appropriate phase and re-run; the output review gate is presented again after the re-run completes.

#### Scenario: Output review accepted
- **WHEN** the user selects Accept at the output review gate
- **THEN** the CLI SHALL exit with status code 0
- **AND** `reports/generation-summary.json` SHALL set `"outputReview": { "status": "accepted" }`

#### Scenario: Re-run from Phase 3 selected
- **WHEN** the user selects `--from-phase 3` at the output review gate
- **THEN** the Rollback Agent SHALL restore the Phase 2 checkpoint
- **AND** the pipeline SHALL execute Phase 3 onward in full
- **AND** the output review gate SHALL be presented again after Phase 6 completes

#### Scenario: Retry specific components
- **WHEN** the user selects `--retry-components Button,Modal` at the output review gate
- **THEN** the pipeline SHALL run the Design-to-Code and Component Factory crews for `Button` and `Modal` only
- **AND** SHALL NOT re-run the DS Bootstrap Crew, Token Engine Crew, or any Phase 4–6 crew
- **AND** the output review gate SHALL be presented again after the targeted retry completes
